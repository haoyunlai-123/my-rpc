# 手写 RPC Framework

> 基于 Netty + ZooKeeper + 自定义协议实现的高性能 RPC 框架
> 支持多种序列化、负载均衡、限流、重试、熔断等扩展能力

------

#  项目背景

在阅读 Dubbo / gRPC 源码并理解其设计思路后，我尝试实现一个**最小可用但具备工程扩展性的 RPC 框架**。

目标不是简单实现远程调用，而是：

- 深入理解 RPC 底层通信模型
- 自定义协议与编解码
- 解决 TCP 粘包拆包问题
- 实现可扩展的组件体系（SPI）
- 实现容错机制（限流 / 重试 / 熔断）

------

# 核心架构

```
Client (Proxy)
   ↓
NettyRpcClient
   ↓
自定义协议编码
   ↓
网络传输
   ↓
NettyRpcServer
   ↓
请求分发 + 反射调用
   ↓
返回响应
```

同时结合：

- ZooKeeper 作为注册中心
- 本地缓存 + Watcher 实现动态更新
- SPI 实现可插拔扩展机制

------

# 核心设计点

------

## 自定义 RPC 协议设计

为解决 TCP 粘包拆包问题，设计自定义二进制协议：

| 字段        | 字节数 | 说明                        |
| ----------- | ------ | --------------------------- |
| 魔法数      | 4      | 校验是否为合法 RPC 请求     |
| 版本号      | 1      | 协议版本控制                |
| Full Length | 4      | 报文总长度                  |
| 消息类型    | 1      | 请求 / 响应 / 心跳          |
| 序列化类型  | 1      | Kryo / Hessian / Protostuff |
| 压缩类型    | 1      | Gzip 等                     |
| 请求ID      | 4      | 用于异步匹配                |

通过：

```java
LengthFieldBasedFrameDecoder
```

精准解决粘包拆包问题。

------

## Netty 线程模型设计

选择 Netty 的原因：

- RPC 属于 IO 密集型场景
- 阻塞模型线程数不可控
- Netty 基于 NIO 多路复用
- 精准控制 EventLoop 线程

实现：

- 自定义 ChannelPool
- 心跳机制
- Channel 复用

------

## 服务注册与发现（ZooKeeper）

- 服务启动时注册临时节点
- 客户端启动时拉取服务列表
- 本地缓存 + Watcher 实现动态更新
- 避免频繁访问 ZK

实现类：

```
ZkServiceProvider
```

------

## 动态代理实现远程调用

使用 JDK 动态代理：

- 屏蔽远程调用细节
- 用户调用本地接口
- 自动构造 RpcRequest
- 异步发送并等待响应

实现真正的：

> 像调用本地方法一样调用远程服务

------

## 可扩展 SPI 机制

自定义 SPI：

- 负载均衡策略
- 序列化方式
- 注册中心实现
- 限流策略

支持通过配置文件动态切换实现。

------

# 容错机制设计

------

##  重试机制

区分：

- 幂等接口（可重试）
- 非幂等接口（禁止重试）

支持：

- 指定异常类型重试
- 指定次数
- 切换 upstream

使用：

```
guava-retrying
```

------

## 限流

实现：

- 计数器限流
- 滑动窗口
- 令牌桶（推荐）

基于：

```
Guava RateLimiter
```

用于保护服务端资源。

------

## 熔断机制

解决服务雪崩问题。

状态机设计：

```
CLOSED → OPEN → HALF_OPEN
```

支持模式：

- 异常比例
- 异常次数
- 慢调用比例

------

#  负载均衡策略

支持多种算法：

- Random
- RoundRobin
- Consistent Hash

一致性 Hash 解决：

- 会话保持
- 节点变更影响最小化

------

# 多序列化支持

支持：

- Kryo
- Hessian
- Protostuff

可通过 SPI 动态扩展。
